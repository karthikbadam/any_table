# Making any_table AI-first: what we learned from `nteract/semiotic`

## Why this matters

We want an LLM (Claude, Cursor, Copilot) to be able to generate a complete,
working `any_table` call from a single natural-language prompt. Today that
requires authoring JSX render props — a shape LLMs produce unreliably. Semiotic
solved the equivalent problem for data visualization. This doc captures the
patterns we studied in their repo and the concrete changes we made to adopt them
here.

## What semiotic actually is

Semiotic is a React viz library built on four composable primitives:
`XYFrame`, `OrdinalFrame`, `NetworkFrame`, `GeoFrame`. Instead of shipping 38
specialized chart components, it exposes those four *frames* and lets you
configure them via props: `type: "bar" | "line" | "area" | ...`, plus
`data`, `xAccessor`, `yAccessor`, `colorBy`, `theme`, `tooltip`, and so on.

The bet pays off for AI: the surface an LLM has to learn is small, the
vocabulary is universal across chart types, and every field is a string, number,
boolean, or plain object — so the LLM can emit the whole thing as JSON-ish
React code without authoring callbacks or layout logic.

## The seven patterns worth copying

### 1. Declarative, JSON-serializable props

Semiotic charts are configured entirely via props — no method chaining, no
imperative setup, no mandatory render-prop children. An LLM that can emit JSON
can emit a chart. We applied this by adding `<AnyTable spec={TableSpec}/>`,
where `TableSpec` is a plain object.

### 2. String accessors over functions

`xAccessor="month"` works directly on raw rows. In our world the analog is
`cell: "number"` — a string name that resolves to a React component via a
registry. Strings survive JSON round-trips and are trivially generated by LLMs.

### 3. Universal vocabulary across components

Every semiotic frame shares `colorBy`, `theme`, `tooltip`, `linkedHover`. A
model learns the vocabulary once and applies it to any chart. Our
`TableSpec` picks a small, fixed set of top-level keys: `data`, `rowKey`,
`columns`, `expansion`, `selection`, `sort`, `rowHeight`, `height`, `theme`.

### 4. Composable primitives > specialized chart types

Rather than ship a `StackedBarChart`, semiotic configures `OrdinalFrame` with
`type: "bar"`, `stack`, `group`. We followed the analog at the cell layer: one
`<AnyTable>` renders every table shape, and a *cell registry* holds the
specialized renderers keyed by string name.

### 5. Machine-readable schema + runtime validator

`ai/schema.json` is the JSON Schema form of the API. `diagnoseConfig()` walks a
spec at runtime and emits errors/warnings for 12+ anti-patterns. Both give an
LLM a way to self-check before or after code generation. We built both, with
Zod as the single source of truth — `z.toJSONSchema()` emits
`packages/react/ai/schema.json` as a build step, guaranteeing drift-free docs.

### 6. Auto-generated LLM instruction files

Semiotic ships `llms.txt`, `claude.md`, and `.cursorrules` alongside the
library. These are plain text, scan-friendly, model-specific. We added
`packages/react/ai/llms.txt` (universal) and `packages/react/ai/claude.md`
(Claude conventions). Both are exported from `package.json#exports` so tools
can fetch them without guessing paths.

### 7. MCP server exposing the library as tools

Semiotic's `semiotic()` MCP tool lets Claude render a chart without hopping
through code generation + compilation. We mirrored this with
`@any_table/mcp`, a stdio server that exposes four tools:

- `any_table.get_schema()` — return the JSON Schema.
- `any_table.list_cells()` — enumerate registered cell renderers.
- `any_table.validate_spec(spec)` — run `diagnoseConfig`.
- `any_table.render_table(spec)` — validate and return a serialized preview.

## Mapping, at a glance

| Semiotic pattern                   | any_table equivalent                                         |
| ---------------------------------- | ------------------------------------------------------------ |
| `XYFrame` / `OrdinalFrame` / etc.  | `<AnyTable spec={...} />`                                    |
| `xAccessor="month"`                | `{ key: "month" }`                                           |
| `colorBy: "product"`               | `cell: { name: "enumBadge", options: { map: {...} } }`       |
| `theme: "tufte"`                   | `theme: "light" \| "dark" \| "auto"`                         |
| `tooltip: true`                    | `expansion: { expandedRowHeight: 300 }`                      |
| `ai/schema.json`                   | `packages/react/ai/schema.json` (generated from Zod)         |
| `diagnoseConfig(props)`            | `diagnoseConfig(spec)`                                       |
| `llms.txt` / `claude.md`           | `packages/react/ai/llms.txt` / `claude.md`                   |
| `semiotic()` MCP tool              | `any_table.render_table()` / `validate_spec()` / etc.        |

## What we kept

- `useTable` + `<Table.*>` compound components are untouched. `<AnyTable>` is a
  thin wrapper, not a replacement. Power users who need non-uniform header
  layouts, custom row rendering, or full styling control use the low-level
  surface as before.
- `packages/core` is entirely unchanged. The declarative layer lives in
  `packages/react/src/declarative/`.
- Existing demos (RubricsDemo, TracesDemo, CustomCellsDemo, SearchDemo,
  CrossFilterDemo) continue to work unmodified.

## What we explicitly did not do

- **No NL-to-spec helper.** Claude composes the spec from `llms.txt` and the
  schema; we don't ship a "turn this sentence into a spec" function.
- **No AI-based type inference from data samples.** Cell type selection is a
  rule in `claude.md`, not a runtime feature.
- **No cross-table linked hover or shared selection.** Out of scope for the
  AI-first layer; can be added later on top of Mosaic if needed.
- **No runtime schema server.** `schema.json` is a static file shipped via
  `package.json#exports`.

## Weaknesses in semiotic's approach we avoided

- **Accessor functions leak back in.** Semiotic's `xAccessor` accepts a
  function (e.g. `(d) => new Date(d.ts)`). This works but forces LLMs to reason
  about code, not data. We kept our string-name registry strict: if a built-in
  doesn't cover the case, register a custom cell once and reference it by name.
- **Frame-prop depth.** Advanced semiotic usage dives into `frameProps`, which
  is another surface to memorize. Our MCP server returns a finite vocabulary
  (list_cells + get_schema), so the LLM never has to stumble into undocumented
  territory.

## Verification

- `DeclarativeDemo.tsx` reproduces `RubricsDemo` from a pure JSON spec.
- `diagnoseConfig` is covered by a vitest suite that targets each anti-pattern.
- `packages/react/ai/schema.json` is checked in and has a snapshot test so it
  stays in sync with the Zod source.
- The MCP server has a smoke test for each of its four tools.
